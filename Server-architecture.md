# Server Architecture

The game requires a seamless, persistent, large-scale world that supports high player concurrency without traditional instancing barriers or loading screens. To achieve this it uses a cluster-based distributed server architecture, in which the world is divided into simulation regions handled collaboratively by multiple servers that scale dynamically with workload. This document is the conceptual specification; its concrete Unreal Engine 5 realisation lives in [Server-architecture (Technical)](<Server-architecture (Technical).md>), which is expected to track the concepts described here.

## 1. System overview

The world is divided into a grid of 1 km × 1 km logical regions. These regions are not separate gameplay instances — players and AI can see and act beyond region boundaries — but they define which server is authoritative for what within the backend. Each region is a full vertical column, from the deepest cavern beneath it to the open sky above, and together the columns form the overworld. Each [dungeon](Structures/Dungeons.md) is a separate space of its own, joined to the overworld at its threshold, as section 3.2 describes.

The ecosystem has two layers. The **Master Server** is the control layer: it directs server assignment, routes players, and coordinates persistence, but it never simulates gameplay. The **Cluster Unit Servers** are the simulation layer: each is a headless Unreal dedicated server that runs the real-time gameplay — players, AI, physics, and combat — for one or more regions. A single Cluster Unit Server can own every region and run the whole world on its own; every server added beyond it raises how many players the world can hold, never what the world is. Because regions can be reassigned between servers at runtime, split when one grows too busy, and joined again when it quietens, the architecture scales horizontally as population rises and contracts again when it falls.

## 2. Master Server responsibilities

The Master Server is the authoritative coordinator of the cluster. It maintains the region ownership map that records which Cluster Unit Server controls each region, and it routes players to their recorded simulation owners on login and after committed handoffs. It performs dynamic load balancing by reassigning, splitting, and joining regions in response to live metrics such as player count, CPU time, and AI load, and it decides when a fight across a region boundary should be brought onto one server (section 6.2). It keeps the cluster clock that every server shares. It coordinates persistence but holds no result in memory alone: every ownership change and every exchange of value is committed in the world database (section 7.2), which is the judge of what happened. Finally, it handles failure recovery: when a simulation node stops responding, the Master Server reassigns its regions to a standby and restores the last committed state. In short, it is orchestration and routing over a durable store — not a gameplay simulator.

## 3. Cluster Unit Servers — region simulation

A Cluster Unit Server is a dedicated Unreal simulation node responsible for one or more contiguous regions. Quiet stretches of the world can be consolidated onto a single server that owns many regions at once, while a crowded hotspot can be isolated so that one region runs on its own server for maximum performance. Each server simulates gameplay for the regions it owns, replicates that state to the clients connected to it, synchronises boundary-relevant entity data with neighbouring servers, and periodically sends state to the world database for persistence. Ownership of a region is not fixed: if load climbs past a threshold the Master Server can migrate a region to another server, which is what gives the system its elastic scalability.

### 3.1 Splitting and joining regions

The 1 km region is the default unit of ownership, not the smallest. When a region grows too busy for one server, the Master Server splits it, as long as spare Cluster Unit Servers are available and the split is worth what it costs. A region crowded across its ground splits into quarters, each on its own server, and a quarter can split again, down to a smallest piece set by the overlap a handoff needs on every side. A region busy at several heights at once splits its column into height bands instead: a cavern system with a whole ecosystem of its own beneath a contested surface, a [floating island](Biomes/Floating-islands.md) drifting above it, or a battle fought on the ground and in the air by riders of the [Royal Dragon](Creatures/Royal-dragon.md) and the wing-rig of [Flight](Flight.md).

Every split adds seams, and every seam inside a busy space costs handoffs and cross-server combat traffic. A split is therefore made only where measurement shows that the gain in simulation capacity outweighs that cost, and the Master Server joins the pieces back onto one owner as the crowd thins. When splitting no longer pays, or no server is free, the region falls back on the degradation order of section 6.3.

### 3.2 Domains and dungeons

A region is identified by its domain as well as its position. The overworld is one domain, its columns covering surface, sea, sky, and the caverns below. Each dungeon is a domain of its own, with its own coordinates and with them the impossible interiors that [Dungeons](Structures/Dungeons.md#impossible-interiors) require: its own sky, its own clock, its own gravity, and floors that rearrange themselves without disturbing the ground above. The threshold where a dungeon meets the overworld is an explicit link between the two domains and serves as a handoff edge, so walking through a dungeon's door is an ordinary transfer rather than a load. A dungeon domain is shared space like the overworld, never a private copy made for one party, and it splits and joins under load like any other region.

Three grids are kept apart. The ownership regions decide which server is authoritative; the content-streaming cells decide which parts of the world are loaded; and the replication cells decide which clients hear about which entities. Each is tuned on its own, so the size of a streaming cell says nothing about who owns the ground.

## 4. Visibility-driven cross-region synchronisation

For the world to feel continuous, a server must know about gameplay happening just across its borders. That synchronisation is driven by visibility rather than by a fixed distance margin, so bandwidth is spent only where something could actually be perceived.

### 4.1 Entity visibility radius

Every network-relevant entity — a player, an AI, a boss, a projectile, even a persistent VFX object — is assigned a visibility radius: the furthest range at which it can be meaningfully seen or interacted with. As resting baselines, players and humanoid NPCs use a medium radius, large world bosses a long one, and small projectiles a short one.

Crucially, this radius is **not a fixed sphere**. It is velocity-aware and directional, following the adaptive model described in [Dynamic culling and render distance](Dynamic-culling-and-render-distance.md): as an entity speeds up, its radius grows and stretches forward along its direction of travel, so the entity becomes relevant earlier on its leading edge while its trailing edge stays near the baseline. Entities fall into the same three categories used for rendering. A stationary or slow entity keeps a symmetric sphere; a fast ground entity is given a forward-elongated volume scaled to its ground speed; and a fast aerial entity — a flying mount at full speed, or a [Flying leviathan](Creatures/Flying-leviathan.md) in one of its short bursts — receives the largest forward extension, because it travels fastest and is usually viewed against open sky. Size is a separate matter from speed: the leviathan drifts slowly most of the time, but its 80-metre body is visible from very far away, so it takes the long, world-boss baseline radius rather than depending on look-ahead. Using one shared radius for both client rendering and server relevancy keeps what a player sees and what a server simulates in agreement.

### 4.2 Sync algorithm

For each entity inside a region the owning server computes the entity's current visibility volume — its baseline radius, grown and extended forward according to its velocity — and tests whether that volume overlaps a neighbouring region. Because the volume reaches farther ahead for fast movers, an approaching entity registers an overlap well before it arrives at the border. The server then checks whether the neighbouring region holds anyone who could perceive the entity, a player or an AI with the matching sense, before sending anything. When an entity could be perceived across the boundary, the server sends a lightweight snapshot of its state to the neighbouring region's server. That server holds the entity as a **non-authoritative ghost**, used only to display the entity to its own players and to let its AI react to nearby external threats and targets. Entities that are out of range of every external perceiver are never synchronised, which is what keeps bandwidth and CPU proportional to what players and creatures can actually perceive.

### 4.3 Long-range presence

An entity with a long radius would otherwise pour its full state across a great many servers. A world boss's radius of roughly 5 km covers some eighty regions, and at a boss fight those regions are at their busiest. Synchronisation therefore runs in two tiers. Within the interaction band, 1,5 km by default and the same as a player's own medium radius, neighbours hold a full ghost that their players can target, fight, and react to. Beyond it they hold a presence ghost: its position, its pose, and the few states that change how it looks and sounds, refreshed about twice a second, which is enough to draw a dragon wheeling over a far ridge or to carry its roar across a valley. A presence ghost can be seen and heard but never targeted, since nothing that far away can reach it anyway.

Ghost snapshots go once to each server that holds a perceiver in range, never once per region, so the worst case grows with the number of servers watching, not with the area the radius covers. The fight around a boss is a separate matter from its silhouette: it follows the combat rules of section 6, which keep it on as few servers as capacity allows.

### 4.4 Relevance beyond sight

Sight is only one way for something to matter to someone. The architecture carries four kinds of information across server boundaries, each with its own reach.

- **Sight** follows the visibility volume and the ghosts described above.
- **Perception events** carry sounds and other sensed happenings — a howl, a horn, a collapsing wall, the song of the [Mermaid](Creatures/Mermaid.md) — as single messages with their own reach, delivered to every server that holds a perceiver inside it. [Audio Direction](Audio-direction.md) makes sound gameplay information, so a player must hear a pack calling from a region where nothing can be seen.
- **Interactions** are requests to the owner of whatever they affect, never changes made to a ghost, as section 6 sets out.
- **Bonds** are lasting relationships between particular entities: a [Royal Dragon](Creatures/Royal-dragon.md) and its mate, a tamed creature and its keeper. Messages between them are addressed by the entity's identity and routed through the ownership record at any distance, so a dragon learns its mate has been harmed though a hundred regions lie between them.

What an entity looks like to one particular viewer, such as the Mermaid's glamour, is decided by its owner and delivered to that viewer alone. Ghosts carry only what anyone nearby could perceive: a neighbour sees the armour a player wears and the weapon in their hand, never the contents of their bag, their bank, their skills, or the maps they have drawn through [Cartography](Skills/Artisan/Cartography.md). That private state lives only with the owning server and the player's own client.

## 5. Seamless player & AI handoff

Movable entities transfer between servers within a bounded simulation overlap around a region boundary. The region grid assigns responsibility for the world, while each entity has one recorded simulation owner. Inside the overlap that owner can differ from the server assigned to the entity's geographic region. The owner continues gameplay simulation and neighbours hold non-authoritative ghosts. Crossing between regions already owned by the same server requires no inter-server transfer.

### 5.1 Stable ownership inside the overlap

Separate forward and reverse transfer thresholds create a deadband, also called hysteresis. An entity arriving from one region keeps its current owner while it remains inside that band, including when it stands still, circles, or repeatedly crosses the map's region line. A transfer becomes eligible only when it moves beyond the threshold toward the destination and that destination is ready. After transfer, returning ownership requires movement beyond the opposite threshold, back toward the previous region. There is no idle timeout that forces a stationary entity to alternate between servers.

The overlap is distinct from the visibility volume. Visibility prepares ghosts at a distance; the simulation overlap defines where an existing owner can safely continue movement and gameplay using loaded world content. Transfer thresholds sit inside that safe area, leaving room to finish a transfer or stop further travel. Fast movers receive earlier preparation and warning. Their speed does not continually move the ownership thresholds beneath them. Region corners select one destination at a time, and an entity has at most one active handoff. Deliberate load balancing and failure recovery use explicit ownership changes rather than repeatedly reclassifying an entity from its position. The same rules hold at the horizontal seams between the height bands of a split column, where a climb, a dive, or a dragon's stoop is the movement that carries an entity across.

### 5.2 Coordinated transfers

The source retains authority while the destination loads the required content and prepares the complete gameplay state. Authority changes at a coordinated cutover; preparation and ghost creation alone never grant ownership. The cutover is a single commit in the world database, so there is exactly one moment at which ownership changes, and a crash on either side, before or after it, leaves one owner and never two (section 7.2). The source retires its authoritative copy after the committed transfer, retaining a ghost where its players still need to see the entity. Movement, health, inventory, active effects, and AI state survive the transfer.

A mount and rider, or a vehicle with its passengers and attached cargo, transfer as one coordinated group. The destination prepares the whole group and its relationships before cutover. Group membership is checked again before commitment so boarding, dismounting, death, or detachment during preparation cannot duplicate or strand a member. Nearby players and enemies remain independent entities; proximity alone does not join them into a transfer group.

The client never reconnects during a handoff. Each player connects through a gateway that holds their one connection for the whole session; behind it, the gateway talks to the server that owns the player and to the neighbouring servers whose ghosts the player can see, and at cutover it switches which server speaks for the player without the client noticing. The [technical guide](<Server-architecture (Technical).md#73-client-connection-continuity>) builds that gateway on Unreal's own multi-server proxy.

### 5.3 Unavailable destinations and visible feedback

If the destination is unavailable, the source keeps simulating entities it still owns within its loaded, bounded overlap. It admits no movement beyond the space it can safely simulate. A player approaching that travel limit sees a translucent holographic error wall with a short message explaining that the region is temporarily unavailable. The warning appears early enough to turn or slow down and becomes more pronounced on approach. The wall marks the actual travel limit, which can lie beyond the nominal region line, and follows the unavailable edge across ground, water, and aerial routes.

The server enforces the limit for movement, including vehicles, AI, and forced displacement. Players can move along the limit or retreat into available space; the display does not grant invulnerability, clear combat, or make the visible wall a climbable world object. Entities already owned by a failed destination follow crash recovery; the neighbouring source does not acquire them merely because it has ghosts.

Combat at the restriction follows one principle: everything with a live owner fights as normal, and nothing owned by the failed server can harm or be harmed. The failed server's entities freeze where they were last seen, grey out, and fade from view after a few seconds. A stale ghost is never a target, never takes damage, and never blocks a shot meant for something live. Arrows, bolts, and spreading effects end at the travel limit as though they had reached the end of their range, and a body knocked into the limit simply stops there, without impact damage, because the limit is not a thing in the world. A player on the healthy side remains exposed to every live attacker, so the wall is never a shelter.

The restriction clears only when the destination can accept gameplay and handoffs again. Recovery restores the failed server's entities from their last committed state and leaves idle overlap residents with their current owners until an ordinary transfer is warranted. Presentation and accessibility details live in [UI and HUD](UI-and-HUD.md#unavailable-region-feedback).

### 5.4 Long-distance transfers and login

Not every move crosses an overlap. A portal or express route from [Travel and Mounts](Travel-and-mounts.md#portals-and-express-routes), a respawn at a bed, claimed point, or bound city from [Death and Loss](Death-and-loss.md), and a login all place an entity somewhere it was not a moment before, so they skip the overlap and use a reserved transfer instead. The source first checks what the jump forbids, such as a cooldown or cargo that may not pass. The destination's owner then reserves the arrival, confirming that the point is valid and has room. The toll, where there is one, is charged in the same commit that changes ownership, and only then does the source retire the traveller. A portal that cannot reserve its far end stays shut, says why, and charges nothing.

A death commits its corpse before the respawn begins, so the body and everything on it exist before the player stands up elsewhere. A respawn point that has been destroyed or made unreachable falls back to the next point the player holds, and finally to their bound city.

A sleeping character, the body that [stays in the world](Death-and-loss.md#logging-out) when its player logs out, is an ordinary persisted entity owned by the region it sleeps in. It is saved with that region, carried through region transfers and restarts like any creature, and can be killed and looted like any other body. A login is routed to the sleeper's owner and the player wakes in it; if it died in the meantime, they wake at their respawn point. Each character holds a single session lease, so it can be played in only one place at a time: a new login revokes the old lease, and any late word from the old session is refused. The subscription of [Monetization and Platforms](Monetization.md#a-single-subscription) is checked when a session starts and as its lease renews, never at a region boundary, so a handoff never becomes a new login and a region move is never an escape from what the body is doing.

## 6. Combat across servers

A full-loot world cannot leave any doubt about who killed whom and who now holds what. Combat across a boundary is therefore governed by fixed rules that depend only on ownership, never on where the region line happens to run.

### 6.1 The target's owner decides

A hit is decided by the owner of whatever is hit. The attacker's server detects the hit against what its players see, ghosts included, and sends a hit claim to the target's owner, stating the attack, the moment it landed, and who made it. The target's owner checks the claim against its own record of where the target was at that moment and alone commits the outcome: damage, wounds, death, the corpse, and the loot on it. The attacker's own costs, such as stamina, arrows, and mana, are committed by the attacker's owner. Because death and its corpse are committed together (section 7.2), a killing blow across a seam can never leave the body on one server and its belongings on another.

The rule is the same for a duel, a skirmish, and a battle of forty players, and the same when attacker and target share a server, where the claim simply never leaves the process. No gameplay rule refers to the region line: there is no protection, timer, or immunity on either side of it, so standing on it gains a player nothing.

### 6.2 Fights dissolve seams

A claim across a seam adds a few milliseconds and extra traffic to every hit, which a long battle should not have to pay. When fighting across a seam is sustained, the Master Server gives the regions on both sides to one server, which it can always do because one server can own any number of regions, and the fight continues with no seam inside it at all. The regions move whole, by the ordinary region transfer, and return to independent owners once the fight has ended and the load allows. The same pull holds a hostile grip together: a [Kraken](Creatures/Kraken.md) wrapped around a ship asks for its own region and the ship's to share a server, and if they cannot, the grip breaks at the handoff. Bringing a fight onto one server is bounded by that server's capacity. A battle too large for one server is split instead, as section 3.1 describes, and fights on across servers by hit claims alone, which remain correct, only costlier.

### 6.3 Hotspots and graceful degradation

A crowd is met first by joining, then by splitting, and only then by degrading. When a busy space can be split no further, or no server is free to take a piece, its region sheds work in a fixed order: cosmetic effects and ambient life first, then the update rate of low-priority AI, then the replication rate of distant entities. If that is not enough, the region's clock slows. Under this time dilation everything inside the region runs at the same reduced pace, its timers included, so a battle slows down rather than breaking apart. Only when time dilation reaches its floor does the region stop admitting new arrivals, holding them at its edge behind the same holographic wall that marks an unavailable region. Some things are never shed at any stage: city guards keep their protection, the warning windows of attacks such as [Thunder](Magic/Spells/Lightning/Thunder.md) keep their full length, and persistence keeps its pace. The representative workloads that set these thresholds are listed in [Server Settings](Server-settings.md#hotspot-workloads-and-degradation).

### 6.4 Timed effects

Spells and other effects that unfold over time are entities in their own right, each with one owner and a timeline set on the cluster clock: when it begins, when its warning shows, when it strikes, and when it ends. Every server presents the same timeline from the same timestamps, so the warning before Thunder lands lasts as long for a player across the seam as for one standing beside the caster.

Effects bound to their caster, such as the channel of [Mending Light](Magic/Spells/Light/Mending-light.md), live with the caster and end if the caster's owner fails; mana already spent stays spent. Effects placed in the world, such as [Flame Wall](Magic/Spells/Fire/Flame-wall.md) and [Static Field](Magic/Spells/Lightning/Static-field.md), are owned where they are anchored and persist on their own, whatever becomes of the caster, and changes they make to the world, such as the fire a Flame Wall spreads or the hazard a [Gust](Magic/Spells/Wind/Gust.md) drives, are committed by the owner of the ground affected. An effect's results on a target go to the target's owner as claims, like any hit, while the effect keeps its own per-target tallies, such as how much healing Mending Light has delivered and so charged for. Every effect records its caster and the membership of the caster's group at the moment of casting, so [Frostbind](Magic/Spells/Water/Frostbind.md) spares exactly those who were allies when it was cast, and the credit for what an effect does goes to whoever cast it.

## 7. Persistence, backups, and recovery

World state is saved continuously, and the rule that governs it is simple: anything that carries value is committed whole, at once, and only once.

### 7.1 Continuous state

Cluster Unit Servers send periodic delta updates — changes only — to the world database, and a region transfer triggers a full serialisation as its handoff payload. The persisted data includes player inventories, stats, and affiliation; AI persistent state such as whether a creature is alive and any lasting changes to its behaviour; and player-placed objects or other environmental changes. The periodic deltas carry only state that can be replayed without harm, such as positions, survival needs, and the progress of a walk across a field.

### 7.2 Value never splits

Every event that moves value commits as one atomic transaction in the world database before its result is shown, and carries an identity of its own so that a retried message repeats nothing. That covers a death and its loot, a trade between players, a sale or purchase in the markets and auction houses of [Great Cities](Structures/Great-cities.md), a bank deposit, a crafted item together with the materials and station charge it consumed, the depletion of a resource node together with the skill practice it earned, and a deposit into the [Item Box](Magic/Spells/Misc/Item-box.md). A transaction checks the state it depends on as it commits — that the bag still has room, that the station still stands, that the seller still holds the goods — and fails whole if any of it has changed, so two players taking the last item from one chest cannot both succeed. Ownership changes at a handoff commit the same way, stamped with an ownership generation, so a server that has lost an entity can no longer write anything for it.

A crash can therefore rewind a few seconds of movement but never split or duplicate an item. A completed sale cannot come back as the seller's goods while the buyer keeps the copy, and an Item Box deposit racing the depositor's death ends with every item in exactly one place: in the box if the deposit committed first, on the corpse if the death did. A settlement market's own ledger of stock and prices is ordinary region state and can lose the trades since its last snapshot, but the coin and goods that changed hands in those trades cannot.

### 7.3 Player-built structures

Player-built structures are a persistence subsystem of their own, because a seamless world full of bases is a heavier load than any population of creatures. A structure's records are its truth, and its actors are only their view, rebuilt from the records whenever its ground is loaded, as the [Building System (Technical)](<Building-system (Technical).md#10-rendering-replication-and-persistence>) sets out. A base has one owner, the server of the region that holds its claim marker, even where its pieces cross into a neighbouring region; edits and damage from the far side reach it as requests, so stability and collapse are always reckoned in one place. A base built on a carrier, the deck of a [Flying Leviathan](Creatures/Flying-leviathan.md) or the shell of a [Titan Turtle](Creatures/Titan-turtle.md), travels in its carrier's transfer group together with its stored contents and everyone standing on it.

Growth is bounded by the design's own rules. Upkeep, weathering, and the piece ceiling of every claim mean that a world's structures track what its players actually maintain rather than everything ever built, and abandoned bases decay out of the database as they decay out of the world. A collapse is written as one batch. Pieces left without a valid base after a crash are found when their region loads and fall under the rules for unclaimed pieces.

### 7.4 Failure and recovery

If a simulation node fails, the Master Server assigns its regions to a standby server, the last committed state is loaded, and affected players are carried back by the gateway with only a brief pause. An outage must never become a weapon. While a region is down, every timer inside it stops: corpse recovery windows, raid objectives and siege timers, upkeep and decay, the slow weakening of a creature bond. The region is closed to attackers and defenders alike, so a sleeping base inside it can be neither raided nor rescued, and when the region returns, every timer resumes where it stopped.

## 8. Shared world state

Some state belongs to no single region. The cluster clock is kept by the Master Server and shared by every server, so day and night, seasons, and every timed effect agree across the world. Weather is computed from the world's seed and that clock, so every server arrives at the same rain over the same hills without exchanging a message; only changes players make to it locally, such as a spreading fire, are owned by the region where they happen. The economy needs no simulator of its own. Each settlement's market is a ledger of stock, prices, and recent trade owned by the server that owns the settlement's region, persisted with that region and carried with it when it migrates, as [Economy and Trade](Economy.md#where-the-market-lives) sets out; regions exchange only slow demand signals summarised over hours, so no market ever waits on another. Bank accounts and auction listings are rows in the world database, and every deposit, sale, and winning bid is a value transaction of section 7.2 committed by the server that owns the bank or auction house. Parties, guilds, alliances, permissions, and ownership of claims and tames are kept by a backend social service as versioned records and pushed to every server. An action is checked against the version its server holds, and anything that grants access to another's property, such as opening a guild chest, is checked again by the owner of that property, so a member removed from a guild cannot slip one last withdrawal through a stale record.

One outcome yields its consequences once. A death or a completed quest is a single outcome event with an identity of its own, committed by the owner who decided it, and the experience, quest credit, and bounty payments that follow from it are derived from that event exactly once, however many servers watched it happen. Standing with an NPC faction is the one consequence that waits. Only an act toward a faction's own people can move it, and only once the encounter has ended with one of them alive and free to tell of it, as the [Reputation System](Reputation-system.md#witnesses) sets out. The owner of the act records which of the faction's people perceived it, by sight or through the perception events of section 4.4, each witness's own owner answers for whether that witness survived, and the change in standing is then derived once from the same event. The death of a player at another player's hands moves no standing at all. Jurisdiction belongs to places, not to regions: the safe areas where city guards intervene under [Conflict and PvP](Conflict-and-pvp.md#safe-cities-and-the-reach-of-the-guard), the claims of the [Building System](Building-system.md), and a guild's negotiated access all keep their bounds wherever the region lines are drawn, and a split never moves them.

The world goes on where nobody is looking, but it is not simulated there. Every record that changes with time — a settlement's population, a bond, a resource node, a creature raised in a stable — carries the time it was last brought up to date, and when its ground is next loaded, the elapsed time is applied by the rules of its own system: bonds hold or weaken as [Taming and Control](Taming-and-control.md) sets out, and settlements repopulate on their own clock under [Settlement Generation](Settlement-generation.md). An NPC convoy of [NPCs](NPCs.md) crossing empty country moves along its route as a record kept by the owner of the region it is crossing, and whether it arrives or is lost is settled when it is due, so a missing convoy still has consequences though no player saw it vanish. Boss-trigger history and each dungeon's clock are durable state of their own domain, kept in the world database rather than in any server's memory.

## 9. Scale and running cost

The cluster's cost follows its players, not its map. Server streaming loads only the ground where players and active creatures are, quiet regions are consolidated onto few servers, and a world with a small population runs on a small cluster. The smallest deployment is one Master Server and one Cluster Unit Server owning every region, which is exactly what a small community server runs, as [Server Settings](Server-settings.md#official-and-community-servers) describes; every further server only adds capacity. The expensive pieces — splitting busy regions, bringing fights onto one server, the gateway's routes to neighbours — are paid only where a crowd has gathered.

The world of a release is open in full from its first day, with no ground held back behind artificial gates; how much world a release contains is set by [Launch Scope](Launch-scope.md), which opens further biomes as frontier expansions after launch. Each world has a population cap, and when a world fills, a new world is opened rather than spreading one crowd across a map too large for it. If multi-server handoff is not yet proven when a world opens, that world runs on a single Cluster Unit Server under a lower cap, and handoff is switched on later without changing any content or rule.

## 10. Why this system works

The architecture borrows proven large-scale MMO ideas and layers on a custom visibility-driven simulation model that keeps Unreal Engine performance feasible. It scales dynamically, absorbing both quiet worlds and sudden mass-player events; it preserves seamless continuity, so players never see the seams between regions; it keeps every fight and every trade under one owner's judgement, so full loot is never in doubt; and it uses bandwidth efficiently, because synchronisation follows per-entity visibility rather than an arbitrary fixed margin. The velocity-aware visibility radius is central to all of this: it prevents pop-in for fast entities, it gives cross-region handoff the lead time it needs to stay invisible, and it ensures the cluster only ever spends resources on entities that some player or AI could genuinely perceive. The result supports genuinely massive open-world gameplay, with AI, combat, and world events spanning many kilometres without overwhelming any single server.

## 11. One-paragraph summary

The game uses a distributed cluster server architecture in which the world is divided into 1 km² simulation regions, each a full vertical column, with every dungeon a domain of its own. A Master Server manages routing, the shared clock, and dynamic load balancing over a world database that judges every ownership change and every exchange of value, while one or more Cluster Unit Servers simulate gameplay, splitting busy regions and joining quiet ones as the crowd moves. Servers exchange only perceivable data, using a per-entity render distance that is velocity-aware and directional, so that players and AI in different regions perceive and interact with one another, fast entities are synchronised early enough for handoffs to stay seamless, and the owner of whatever is struck alone decides the outcome of a hit.
